# Elucient Setup

## Stack

- **Payload CMS** 3.86.0 — headless CMS, integrated into Next.js via `@payloadcms/next`
- **Next.js** 16.2.11 — App Router, TypeScript
- **Tailwind CSS** 4.3.3 — CSS-first config, no `tailwind.config.js` needed
- **PostgreSQL** via `@payloadcms/db-postgres` (Drizzle ORM)
- **Package manager**: pnpm


## Key Config Notes

- `next.config.ts` uses `withPayload(config, { devBundleServerPackages: false })` — required for Turbopack compatibility
- `tsconfig.json` has `@payload-config` path alias → `src/payload.config.ts`
- Tailwind v4 uses `@tailwindcss/postcss` in `postcss.config.mjs` instead of the old `tailwindcss` plugin
- `(payload)/layout.tsx` imports from `@payloadcms/next/layouts` — only `RootLayout` and `handleServerFunctions` exist in v3.86.0 (`generatePayloadViewport` does NOT exist)
- Pool `max` is conditional in `payload.config.ts`: `10` in dev, `1` in production (Vercel serverless). See "Database hang root cause" below for why.

## Dev Commands

```bash
pnpm generate:importmap   # Generate admin importMap (run once after adding plugins/collections)
pnpm dev                  # Next.js dev server (Turbopack — default in Next.js 16)
pnpm build                # Production build
pnpm payload              # Payload CLI
```

### importMap note

With Turbopack, the webpack plugin that auto-generates importMap doesn't run. Run `pnpm generate:importmap` once after adding new Payload plugins or collections. Without it, the admin dashboard will throw `PayloadComponent not found in importMap` errors.

**`"type": "module"` in `package.json` is required** for `generate:importmap` to work on Node.js v22. tsx reads the `type` field to decide how to load `.ts` files. Without it, tsx uses the CJS path, which invokes `loadESMFromCJS` (synchronous) for static imports. That sync path bypasses tsx's ESM hooks, so extensionless TypeScript imports like `'./collections/Users'` fail. With `"type": "module"`, tsx uses the ESM path, its async hooks run, and they resolve `.ts` extensions correctly.

## Database

### Local (Docker)

```bash
docker compose up -d    # Start PostgreSQL 16 on port 5432
docker compose down     # Stop
docker compose down -v  # Stop + delete data
```

Connection string in `.env.local`:

```
DATABASE_URI=postgresql://postgres:postgres@127.0.0.1:5432/elucient?sslmode=disable
```

**Important**: use `127.0.0.1`, not `localhost` (avoids IPv6 resolution). Add `?sslmode=disable` to prevent SSL negotiation errors with the older pg client bundled in drizzle-kit.

### Database hang root cause (resolved)

**Symptom**: `[⣻] Pulling schema from database...` spinning forever on `pnpm dev`.

**Root cause**: A deadlock in the pg connection pool:

1. Payload's `connect.js` calls `pool.connect()` to hold a keepalive client → checks out the only slot (`max: 1`)
2. `pushDevSchema` then calls `drizzleInstance.execute()` to introspect the schema → tries to acquire another pool slot → waits forever

**Fix**: `max: 1` is only set in production. In dev, `max: 10` allows both the keepalive connection and schema-push queries to coexist.

**Additional fixes applied**:

- PostgreSQL 16 instead of 17 (better compatibility with pg client)
- `127.0.0.1` instead of `localhost` in DATABASE_URI
- `?sslmode=disable` in DATABASE_URI

### Production (Vercel)

Use **Neon** (Vercel Postgres is Neon under the hood):

- Vercel Dashboard → Storage → Create Database → Postgres
- Use the **pooled** connection string (critical for serverless)
- Set `DATABASE_URI` in Vercel environment variables

Payload runs Drizzle migrations automatically on first `pnpm dev` — no manual migration step needed.

## Environment Variables

Copy `.env.example` → `.env.local` and fill in:

```
DATABASE_URI=       # PostgreSQL connection string
PAYLOAD_SECRET=     # Min 32 chars, random string
NEXT_PUBLIC_SERVER_URL=http://localhost:3000
```

## Next.js Version Compatibility

Payload 3.86.0 supports specific Next.js versions only:

```
>=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.2.6 <17.0.0
```

Currently pinned to `16.2.11` — do not upgrade Next.js without checking Payload compatibility first.

## Linting & Formatting

- **ESLint 9** (not 10) + `eslint-config-next` — flat config in `eslint.config.mjs`
- **Prettier** — single quotes, no semicolons, trailing commas, 100 chars (`.prettierrc.json`)
- **Husky + lint-staged** — runs on every `git commit` automatically

### Why ESLint 9, not 10

`eslint-config-next` pulls in `eslint-plugin-react@7.x` which uses `context.getFilename()` — removed in ESLint 10. There is no stable `eslint-plugin-react` version that supports ESLint 10 yet. Upgrade ESLint to v10 only after `eslint-config-next` updates its dependency chain.

### lint-staged behaviour

On commit, automatically runs:

- `*.{ts,tsx}` → `eslint --fix` + `prettier --write`
- `*.{js,mjs,cjs}` → `prettier --write`
- `*.{json,css,scss,md}` → `prettier --write`

### Commands

```bash
pnpm lint      # ESLint check (via Next.js CLI)
pnpm format    # Prettier --write on src/
```
